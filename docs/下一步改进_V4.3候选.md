## A 组 · 安全（会真金白银出事）

### A1 密码改 Windows DPAPI ★最高优先级

**现状**：密码存成 `v1:` 前缀的 XOR 混淆串（accounts.encode_password），
**解盐硬编码在 exe 里**。拿到 `config.json` 的人一键就能还原明文门户密码。

**改法**：用 `CryptProtectData`（`ctypes.windll.crypt32`）加密，密钥绑定 Windows 用户账户。

**代价**：换机 / 重装系统 / 换 Windows 用户后必须重新登一次（可接受，界面已有 🔑 入口）。
**兼容**：读入时先认 `v1:` 旧格式，能解开就自动升级成 DPAPI 格式再落盘。

### A2 「抢到即停」的竞态窗口

**现状**：多账号并行时，`stop_on_first=True` 靠一个线程间信号通知其他人收手。
信号传到之前，另一个账号可能已经把请求发出去了 —— 服务端的「每天一单」检查有竞态。

**改法**（二选一）：
- 软：抢到之后立刻去查「我的订单」，多出来的提示用户手动退；
- 硬：抢到后等一个 RTT 再确认，确认成交才广播停止。

**现状缓解**：README 已写明「抢完请到我的订单核对一眼」。默认 `parallel_first=0`（纯串行），
这条只在用户主动开并发时才可能触发。

### A3 一天一单保护只在开抢前查一次

**现状**：`one_per_day` 在开抢前查一次当天订单。挂机过夜场景里，
若昨晚 23:50 已经手动订过一单、早上 8:00 又自动抢，保护逻辑用的还是「开抢前」那一次查询
（那时确实没单），但成交后当天就有两单了。

**改法**：提交成功后立刻复查一次订单数，>1 就在日志和界面上大声告警（不自动退单，
退单要人工确认）。

## B 组 · 速度（抢的是毫秒）

### B1 首枪提前量补偿（F2）

**思路**：用实测单程延迟（RTT/2）把第一发时刻提前到 `T - lead`，
让请求**恰好**在放号瞬间到达服务端，而不是「发出那一刻刚好到」。

**风险**：提前太多会在放号前刷一串 `not_open_yet`，可能踩限流。
→ 做成**默认关闭**的开关 `lead_compensate_ms`，先积累几早上的实测数据（C2 打点已有 RTT）再定默认值。

### B2 放号时刻自学习（F3）

**思路**：连续几天记录「第一发成功 vs 第一发 not_open_yet」的时间戳，
反推服务端真实放号时刻与本机时钟的漂移，替代固定 `08:00:00`。

**配套**：需要一个 `logs/result_*.json`（见 C1）来存每天的第一枪结果，否则没数据可学。

### B3 多账号共享校时（F4）

**现状**：每个账号线程各测一次服务器时钟差（`measure_clock_offset`），
重复发请求，在 T-2s 那个最金贵的窗口里是纯浪费。

**改法**：主线程测一次，各账号线程共享结果。省下 N-1 次往返。

## C 组 · 可观测（没抢到也要能说清为什么）

### C1 结果 JSON 复盘（F5）

把每次抢场的 `result` 结构化写进 `logs/result_YYYYMMDD_HHMMSS.json`：
第一枪时刻 / RTT / verdict / 候选表 / 最终成败。
配合已有的 C2 打点，做成「昨天为什么没抢到」的一页纸诊断。

这也是 B2（放号时刻自学习）的前置条件。

### C2 配置健康检查（F6）

界面上对危险组合直接给出警告：
- `min_interval < 0.13` —— 太密必被限流；
- `auto_refresh_token=false` 却开了定时挂机 —— **隔夜必然 401**（这正是之前 dist/config.json 的状态）；
- 目标日期已过期 / 超出预约窗口；
- 勾了挂机却没有任何一个账号存了密码。

### C3 日志里区分「网络抖动」和「被限流」

现在 `network_error` 和 `rate_limited` 在日志里长得差不多，复盘时容易误判。
建议给限流单独一个前缀（比如 `⚠限流`），一眼能数出被拒了几次。

## D 组 · 工程（不紧急，但迟早要还）

### D1 V4.2 目录还没有 git

V4.1 有自己的 `.git`（推 `v4.1` 分支），**V4.2 目前没有仓库**。
要建的话：照 V4.1 的做法开 `v4.2` 分支，`.gitignore` 必须含 `config.json`、`logs/`、
`.profiles/`、`dist/`、`build/`、`release_zip/`。

### D2 CAS 回跳地址在两处各拼一遍

`booker.py` 和 `browserlogin.py` 各写了一份 service 回跳 URL，改一处会漏另一处。
→ 抽成一个公共函数。

### D3 `/api/login` 是废弃入口

真正的登录入口是 `/api/caslogin`。`/api/login` 留着只是脚本调试用，
建议在注释里写死「无 UI 入口」，避免以后有人误接。

### D5 「登录到底卡在哪一跳」目前只能靠临时脚本

排查 G6（账号四刷新完还是 401）时是现写 `过程文件/diag_acc4_browser.py` 才看清
整条跳转链的。界面上没有等价能力 —— 用户遇到「刷新失败」只能把日志发过来。

→ 建议在「重新获取 token」失败时，把**脱敏后的跳转链**（域名 + 路径 + 是否带
`szblTK`、localStorage 快照指纹）一并写进运行日志，排查就不用再派人写脚本。
低优先，但真出事时省一小时。

### D6 多因子认证账号没有服务端兜底

G6 排查时确认：**账号四开了 MFA**，所以 `booker.api_cas_login()` 对它只会返回
`MFA_REQUIRED`，不能拿它给浏览器路径兜底（当时想过，实测否掉了）。
→ 若以后要支持「无人值守刷新 MFA 账号」，只有两条路：企业微信推送确认，
或者让用户预先在浏览器里勾「信任此设备」并定期维护档案。都超出当前范围。

### D4 exe 控制台输出在重定向时读不到

验收时发现的：把 exe 的 stdout 重定向到文件后，启动横幅读出来是空的（Python 块缓冲，
`PYTHONUNBUFFERED=1` 对 PyInstaller 打包的 exe 也没生效）。
→ 想验证「exe 是不是新代码」，别搜二进制也别指望 stdout，用**行为断言**
（比如请求某个只有新版才有的字段）。`过程文件/e4_acceptance_v42.py` 就是这么做的。
